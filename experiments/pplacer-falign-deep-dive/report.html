pplacer_testsuite's falign slowdown is real — and it's not icache

The standing theory (since the original falign report) was "incidental code-alignment / icache-layout artifact." Verified directly with hardware counters and topdown analysis: every cache/TLB/branch-miss counter improves under falign. The actual cost is front-end fetch/decode bandwidth — a blanket tax from padding every function to a 64-byte boundary, diffuse across dozens of functions rather than concentrated in one hot path.

Frontend Bound rises, Bad Speculation falls (matches the branch-miss decrease above), Retiring stays flat (matches the flat instruction count). Textbook signature of a fetch/decode-bandwidth bottleneck — the pipeline is measurably more often stalled waiting for instructions to arrive, not waiting on memory or recovering from mispredicts. Bars above are relative-share illustrations from the raw topdown slot counts in results.md; measured via perf stat -M tma_frontend_bound etc., one metric group at a time (r=10) to avoid PMU multiplexing noise.

Where: diffuse, not concentrated

Caveat first: the raw flamegraph diff below is partly misleading. [unknown]-attributed weight nearly doubles under falign (5.02B → 8.91B weighted samples, +77%) — DWARF unwind resolution gets measurably worse on the falign binary for some samples, and the naive top-mover list ([unknown];do_some_marking apparently jumping from 0 to 3.9B) is substantially this artifact, not a real new cost.

No single hot path stands out beyond its existing share of runtime — do_some_marking grows the most in absolute terms only because it's already 64.5% of the program (pplacer is GC-heavy: GSL vectors, sqlite3 handles, and Gc.finalise all over its hot path). Everything else is a long, diffuse tail of unrelated functions — GC internals, GSL, OCaml stdlib parsing/lexing, memcmp, malloc — each a little bigger. Exactly the signature of a blanket per-function code-size tax, not a targeted regression.

Mitigation, given the confirmed mechanism

1

Don't apply -falign-functions=64 globally

Simplest fix, still valid — TASK 3 already showed it's a wash in aggregate (helps frama_c_eva_sqlite -43%, menhir_sql_parser -11.5%; hurts this one and a few others).

2

Try a smaller alignment value (16 or 32 instead of 64)

Now the best-supported option. Since the mechanism is confirmed to be raw padding volume (not layout luck), a smaller value should directly and predictably reduce the front-end tax — worth sweeping on this benchmark specifically.

3

PGO or a post-link layout tool (e.g. LLVM BOLT)

Pads/reorders based on real hot-path profiling instead of uniformly bloating every function — addresses exactly the failure mode found here.

×

Per-function targeted alignment — not a good fit here

Unlike a concentrated regression, this cost is diffuse across dozens of functions. There's no single function to annotate. Stays viable for a different benchmark with a concentrated regression, just not this one.
