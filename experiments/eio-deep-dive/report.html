eio_fiber_stream isn't noisy — it's the mutex primitives

Pinned, repeated measurement (taskset + ASLR off, perf stat -r 30) shows the ±10% spread across fp/falign/auto-compact runtimes is dominated by one real, deterministic effect: --enable-frame-pointers alone adds 9.7% more retired instructions, almost entirely inside caml_ml_mutex_lock/unlock and their underlying pthread calls.

Reading: caml_ml_mutex_lock/unlock live in the OCaml runtime's C source (runtime/sync_posix.c). Building the runtime with --enable-frame-pointers adds a push %rbp; mov %rsp,%rbp … pop %rbp prologue/epilogue to every C function in it — including these. They're tiny, and eio_fiber_stream's 4-producer/4-consumer stream calls them millions of times (“Processed 60,000,000 items”), so the fixed per-call tax dominates far more here than on compute-bound benchmarks, where the suite-wide fp cost is only ~1–2.5%.

Methodology notes

Two environment issues surfaced and were worked around; both are recorded here since they changed which numbers are trustworthy.

1. The original harness numbers included real scheduling/frequency noise. The macro-benches running-ng harness runs unpinned, under the box's default powersave governor (800MHz–5.3GHz range), on a hybrid P-core/E-core CPU (Intel i7-14700). Pinning to a single P-core (taskset -c 3, ASLR off via setarch -R) collapses run-to-run variance to ±0.02% — confirming the harness's wider spread was partly measurement environment, not (only) a real runtime cost. The underlying fp effect is real regardless; pinning just makes it measurable cleanly.

2. perf record initially crashed the benchmark. eio_fiber_stream unconditionally calls io_uring_queue_init at startup (even though its workload never issues ring I/O). perf record's default mmap ring buffer plus that io_uring init both compete for locked memory under this account's fixed 8MB RLIMIT_MEMLOCK (hard limit, no sudo available to raise it) — together they exceeded it, and the benchmark process died with ENOMEM from io_uring_queue_init before doing any work. Fixed with a small ring buffer (perf record -m 4), which left enough headroom for both.

Off-CPU analysis (perf sched record / bpftrace, per Gregg's off-CPU method) was scoped for this investigation but needs root (tracing debugfs permissions) this account doesn't have non-interactively; not run for this report. Given the on-CPU instruction-count story already fully accounts for the wall-time delta (task-clock ≈ wall-clock in every perf stat run — the process is never substantially blocked), it wasn't needed to explain the result, but remains available as a follow-up if you want to double-check.
